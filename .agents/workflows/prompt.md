# Prompt Engineering Workflow

**Activation:** `/prompt` (또는 `/prompt-engineering`, AI 프롬프트의 신규 작성, 템플릿 설계, 구조화된 출력 정의, 성능 최적화 및 디버깅을 진행할 때)

이 워크플로우는 AI 프롬프트의 설계, 템플릿화, 퓨샷(Few-Shot) 구성, 구조화된 출력 스키마 정의, 품질 최적화 및 프로젝트 통합의 전 라이프사이클에 적용되는 마스터 가이드라인입니다. 모호한 자연어 지시를 넘어 **재현 가능하고 신뢰성 높은 프롬프트 아키텍처**를 구축하는 것을 목표로 합니다.

---

## 1. 필수 스킬 참조 및 핵심 원칙 (Core Skills & Principles)

프롬프트 작성 또는 개선 작업 착수 전, 반드시 아래의 공식 프롬프트 엔지니어링 스킬을 확인하고 적용합니다:
- **기본 기법 및 패턴 학습:** `.agents/skills/prompt-engineering/SKILL.md` (CoT, Few-Shot, System Prompt, Error Recovery, Progressive Disclosure)
- **고급 프로덕션 패턴 학습:** `.agents/skills/prompt-engineering-patterns/SKILL.md` (JSON Mode, Pydantic/Zod Schema 강제, A/B Testing, Token 최적화, KPI 지표)

### 5대 설계 원칙
1. **구체성 (Be Specific):** 모호한 지시는 모호한 결과를 낳습니다. 기대하는 출력의 어조, 포맷, 길이를 명시합니다.
2. **시연 중심 (Show, Don't Tell):** 긴 서술형 설명보다 실제 입출력 예시(Few-Shot)가 훨씬 강력합니다.
3. **지침 계층화 (Instruction Hierarchy):** 역할, 작업, 제약, 예시, 입력 데이터의 순서로 문맥을 체계화합니다.
4. **구조화된 출력 강제 (Structured Output):** 파싱이 필요한 결과물은 반드시 JSON/Schema를 강제하고 예외 처리를 둡니다.
5. **토큰 효율성 (Token Efficiency):** 컨텍스트 윈도우를 낭비하지 않도록 간결하면서도 본질적인 지시를 유지합니다.

## 2. 역할 및 시스템 프롬프트 아키텍처 (Role & System Context)

- **명확한 페르소나 부여:**
  - AI 모델의 전문성과 행동 기준을 시스템 컨텍스트에 정의합니다.
  - *예시:* "당신은 교육 자료와 노트를 디지털 학습 덱(JSON)으로 정밀하게 변환하는 전문 교육 데이터 엔지니어입니다."
- **부정적 제약 조건(Negative Constraints) 명시:**
  - 하지 말아야 할 행동을 명확한 금지 규칙으로 선언합니다.
  - *예시:* "인사말이나 부연 설명을 덧붙이지 마십시오.", "주어진 텍스트 외의 내용을 임의로 지어내지 마십시오."
- **시스템 프롬프트와 사용자 프롬프트의 분리:**
  - 변하지 않는 역할 및 지침은 시스템 프롬프트(또는 템플릿 상단)에 배치하고, 가변적인 사용자 입력 데이터는 명확히 격리합니다.

---

## 3. 지침 계층 구조 및 추론 설계 (Instruction Hierarchy & Reasoning)

프롬프트는 다음의 표준 계층 구조를 따릅니다:

```
[System Context / Role]
  ↓
[Task Instruction (주 작업 지침)]
  ↓
[Negative Constraints / Rules (제약 조건 및 금지 사항)]
  ↓
[Few-Shot Examples (입출력 모범 사례)]
  ↓
[Input Data (처리할 실제 데이터)]
  ↓
[Output Format / Schema (최종 응답 형식)]
```

### Chain-of-Thought (CoT) 적용 기준
- 단순 사실 검색이나 포맷 변환이 아닌, **분석/추론/다단계 검증**이 필요한 작업에는 반드시 단계별 사고를 유도합니다.
- 복잡한 문제 풀이, 오답 원인 분석, 비정형 텍스트의 구조화 작업 시 "단계별로 생각하십시오(Let's think step by step)" 또는 세부 단계(Step 1, Step 2...)를 프롬프트에 내장합니다.
- 복잡도에 따라 제약 조건과 예시를 점진적으로 심화하는 점진적 공개(Progressive Disclosure) 기법을 활용합니다.

---

## 4. Few-Shot 예시 구성 (Demonstrations)

- **2~5개 입력-출력 쌍 구성:**
  - 모델에게 원하는 형태와 품질 수준을 직접 보여주기 위해 정제된 예시를 포함합니다.
- **다양성과 엣지 케이스 포괄:**
  - 정형적인 케이스뿐만 아니라 줄바꿈, 특수기호, 누락 데이터 등 경계 조건(Edge case)에 대한 처리 예시를 포함합니다.
- **예시 오염(Example Pollution) 방지:**
  - 타겟 도메인과 무관하거나 모델의 편향을 유발할 수 있는 부적절한 예시를 배제합니다.
  - 토큰 낭비를 유발하는 과도한 길이의 예시는 정제하여 핵심만 담습니다.

## 5. 구조화된 출력 및 스키마 강제 (Structured Output & Error Recovery)

- **Zod / JSON Schema와의 일치:**
  - 애플리케이션에서 파싱할 데이터인 경우, 프로젝트의 데이터 모델(Zod 스키마 또는 TypeScript 인터페이스)과 1:1로 일치하는 JSON 포맷을 프롬프트에 기술합니다.
- **순수 JSON 응답 제어:**
  - 마크다운 백틱(````json ... ````) 포함 여부를 명시하고, 파싱 에러를 유발하는 trailing comma, 누락된 따옴표 등이 발생하지 않도록 규칙을 지정합니다.
- **에러 복구(Error Recovery) 지침 내장:**
  - 입력 데이터가 불완전하거나 추출이 불가능할 때의 기본값(Fallback) 또는 오류 메시지 출력 형식을 사전에 정의합니다.
  - *예시:* `자료에서 답을 찾을 수 없는 경우 "해당 정보 없음"으로 표기하십시오.`

---

## 6. 재사용 가능한 템플릿 시스템 (Reusable Template Systems)

- **동적 변수 보간(Interpolation):**
  - 프롬프트 함수는 가변 데이터를 명확한 매개변수(예: `(content: string) => string`, `{question, options, explanation}`)로 전달받아 안전하게 템플릿 리터럴로 조립합니다.
- **모듈형 컴포넌트:**
  - 반복되는 지시문(예: JSON 스키마 가이드, 톤앤매너 설정)은 공통 템플릿 조각으로 분리하여 재사용성을 극대화합니다.

---

## 7. 프로젝트 통합 및 다국어(i18n) 연계 가이드라인 (`memorize_supporter` 전용)

- **UI 텍스트 제로 하드코딩 준수:**
  - 사용자에게 노출되거나 클립보드로 복사되는 모든 프롬프트 템플릿은 `src/i18n/types.ts`에 타입을 정의하고, `ko.ts`, `en.ts`, `ja.ts` 3개 언어 딕셔너리에 100% 동기화합니다.
  - *예시:* 덱 생성 프롬프트(`promptFormat`), 상세 튜터 프롬프트(`aiDeepPrompt`).
- **다국어 프롬프트 뉘앙스 동기화:**
  - 한국어뿐만 아니라 영어, 일본어 프롬프트에서도 대상 LLM이 최상의 성능을 낼 수 있도록 각 언어별 자연스러운 어휘와 명확한 페르소나 지시를 유지합니다.
- **사용자 인터랙션 점검:**
  - 프롬프트 생성 컴포넌트(`aiPromptGenerator`), 클립보드 복사 액션, 안내 토스트(Sonner)와의 사용자 경험(UX) 연결 상태를 확인합니다.

## 8. 품질 검증 및 자가 점검 체크리스트 (Self-Check & QA)

프롬프트 작성 또는 수정 완료 후 아래 체크리스트를 전수 검증합니다:

- [ ] **역할/페르소나 명확성:** 모델이 수행해야 할 역할과 전문 분야가 선언되어 있는가?
- [ ] **지침 명확성:** 작업 목표와 필수 제약(Negative Constraints)이 모호함 없이 기술되었는가?
- [ ] **Few-Shot 예시 적절성:** 2개 이상의 고품질 입력-출력 예시가 포함되어 있는가?
- [ ] **출력 스키마 일치:** 요구되는 JSON 구조나 출력 형식이 프로젝트 스키마와 완벽히 부합하는가?
- [ ] **예외/엣지 케이스 처리:** 불충분한 입력이나 에러 상황에 대한 회복 지침이 마련되어 있는가?
- [ ] **토큰 효율성:** 불필요한 서술이나 중복 문장이 제거되어 간결한가?
- [ ] **다국어(i18n) 무결성:** 프롬프트가 다국어 딕셔너리에 정의되어 있으며 3개 국어(ko/en/ja) 모두 동기화되었는가?
- [ ] **실제 모델 검증:** 작성된 프롬프트를 실제 LLM(Claude, GPT, Gemini 등)에 테스트하여 기대한 스키마와 품질로 출력되는지 확인했는가?
